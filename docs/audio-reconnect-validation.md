## Remaining risks and gates

- A crash after the durable uncertainty marker is stored but before Android receives the call can leave a fence unresolved until trustworthy profile transitions occur; corrupt state also fails closed. There is no validated recovery for every such case.
- A participant paired with an older requester that does not send terminal release can remain reserved after success. The strict v2 HELLO schema prevents silently adding capabilities; mixed-version recovery remains unproven.
- The legacy peer status protocol still uses the optimistic Boolean ownership accessor; its behavior with an unavailable profile proxy needs separate mixed-version review. The v2 snapshot now reports unknown for an unavailable/transitioning A2DP profile and for a disconnected profile with contradictory AACP connectivity, instead of claiming ownership. This change passed automated checks and is installed in the latest APK but is not yet physically verified.
- The command boundary includes synchronous storage and Binder work under the driver lock. Check real callback latency and responsiveness, process death, Bluetooth adapter restart, and missing or out-of-order OEM scan timestamps.
- Hidden A2DP and HEADSET profile method lookup is now confined to `AndroidHiddenProfileCommands`; service-side permission checks, proxy lifetimes and fenced release/secondary-profile callbacks remain. The focused adapter and source-guard tests pass, but the guard is narrow. Audit remaining scheduling and release paths before declaring a single authority complete.
- Run the remaining physical matrix in `audio-reconnect-device-run.md`: repeated online/offline cycles in both directions, screen-off idle, stored versus removed buds, contention, calls/media, lifecycle and HR/relay smoke checks. No notification, audible-route or latency distribution acceptance is established.
- The policy audit found initialization and UI writes to the case-open key, now routed through one source. External changes are labeled without attribution. The historical Xiaomi `feature=false` observation remains unexplained; no conclusion that the user disabled the setting is supported. Real process-death and independently arriving settings updates remain to be verified on devices.
- Recovery research: Android exposes `Settings.Global.BOOT_COUNT` from API 24 (https://developer.android.com/reference/android/provider/Settings.Global#BOOT_COUNT). It could distinguish a device reboot from an app-only restart for newly written markers, but the API reference alone does not establish that a new Bluetooth command is safe after reboot or adapter restart. No fence is cleared on this basis today. Any implementation would need a fresh profile query, behavior for missing/legacy boot counts, and controlled device tests; do not infer command completion from elapsed time or an unavailable boot count.

Analyzer regression coverage now includes two synthetic, overlapping profile-connected reports and verifies that each device's timeline remains separate; seven Python analyzer/source-guard tests pass. These synthetic timestamps do not establish real-world simultaneous ownership or an audible route.

Follow-up: explicit peer snapshot refreshes are now spaced by at least two seconds and capped at five per passive intent; reservation reassessment still runs independently, and normal peer handshake/heartbeat remains unchanged. Focused refresh-budget and acquisition-recovery tests pass. This follow-up is in the revised APK but has not undergone physical validation.
